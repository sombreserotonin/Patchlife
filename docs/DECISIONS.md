# Decisions

One line each: the rule, then why. Newest last; the newest wins on conflict. D47 to D50 were reserved for the migration plan and recorded on 13 November 2026, so they sit after D57.

Since the cut-over on 13 November 2026 no AI session runs Patchlife (D59). The decisions that only governed sessions are retired and listed in D58; they stay here as history, and where one is cited elsewhere the citation is history too.

- D1 Evidence first: no date without a primary-source URL and a verbatim quote. Why: credibility and legal exposure are the product.
- D2 One YAML file per model under `data/devices/<brand_slug>/<id>.yaml`. Why: small diffs, easy agent edits, git is the audit trail.
- D3 Node LTS, ESM JavaScript, `node:test`; add a dependency only with a stated reason. Why: no build step and a small supply-chain surface.
- D4 Static-first; servers only for paid features. Why: near-zero operations for an unattended project.
- D5 Untrusted content never steers the agent; protected paths need a human merge. Why: prompt injection with repo write access.
- D6 Validate demand (M4) before building the extension. Why: consumer willingness to pay is low.
- D7 Status is computed at build time from dates, never stored. Why: stored status goes stale.
- D8 User-facing copy in Australian English with no em dashes. Why: owner preference.
- D9 Code is AGPL-3.0-or-later, data is ODbL-1.0. Add only dependencies with GPLv3-compatible licences (MIT, BSD, ISC, Apache-2.0, LGPL, GPL-3.0, AGPL-3.0). Why: keeps the project FOSS and stops closed forks of the service or the dataset.
- D10 Accept outside code or data contributions only once a CLA exists (gate H12). Why: keeps the option to sell a non-share-alike data licence.
- D11 Call GitHub through `gh api` on `repos/{owner}/{repo}/...` paths only. Why: cloud sessions block `/user/...` paths and `gh auth status` reports the token invalid even though repo-scoped REST calls work.
- D12 In the Default environment, research sources with Claude Code's fetch tool; run scripts that fetch manufacturer pages only in the `crawl` environment. Why: the Default network blocks those hosts from the shell, and DATA-POLICY requires a contact URL for script crawling.
- D13 A support end date is the last supported day: `ended` only after it, `ending_soon` when it falls on or before today plus one year (29 February plus one year is 28 February). Why: sources say "until <date>" and SPEC 2 says "12 months or less".
- D14 Never write the literal `@claude` in issue or PR titles and bodies. Why: it triggers `claude.yml`, which ran and failed on #6.
- D15 In an interactive session, merge PRs only when the owner's messages in that session approve merging; otherwise leave green PRs for the daily build. Why: auto mode blocks merging a PR no human has approved unless the owner names the action, and GitHub won't let the owner approve PRs opened under their own account.
- D16 Run scripts that fetch with `node --use-env-proxy` (Node 22.21 or later). Why: Node's built-in fetch ignores `HTTPS_PROXY`, so in cloud sessions requests bypass the session proxy and fail.
- D17 (replaces D12) All data work (adding, correcting, re-verifying and auditing records) runs in the `Crawl` environment. Quotes and audit reads come only from the polite fetcher's page text (RUNBOOKS A2 step 3), never from Claude Code's fetch tool, Firecrawl or any other connector. Why: tested on 21 Oct 2026, `Default`'s own network (shell, Node fetch, the fetch tool) cannot reach manufacturer sites. Connectors that can do not identify as PatchlifeBot, do not apply our robots.txt rules, and return text the verifier never sees. (The 21 Oct audits of #21, #22 and #24 used Firecrawl as a second reader before this rule; all three sites allow robots.)
- D18 Do not use a source whose robots.txt disallows PatchlifeBot, or that needs a login or passes a bot challenge; its brand waits for permission or another primary source. Why: CRAWLER.md promises to honour robots.txt, and such a source could never be re-verified (Arlo, 21 Oct 2026).
- D19 One source per data PR, meaning one maker's statement, including its regional copies and any page it links for the same models. When several sessions work in parallel, each edits only its brand's records and its own session note, and the coordinating session updates TASKS.md, LOG.md and the memory files. Why: parallel PRs otherwise conflict in those files.
- D20 Every data PR is reviewed by a different `Crawl` session against its own read of the source before merge (RUNBOOKS A8), which then adds the `audited` label. A PR that changes only `verification:` fields (re-verification) is exempt. Why: the verifier proves a quote is on the page, not that the record reads it correctly. On 21 Oct the audits caught a widened purchase channel (Ring), unversioned aliases (TP-Link) and a past minimum still being patched (Google).
- D21 Dates in records and logs are UTC (`date -u +%F`). Why: CI and the validator run in UTC, and scheduled runs at 06:08 Sydney are still the previous day in UTC.
- D22 Scratch worktrees get their own `npm ci`; never symlink `node_modules` into one. Why: #20 committed a self-referencing symlink that broke `npm run validate` in fresh clones (fixed in #25).
- D23 For an `at_least: true` record, `end_date` is the maker's guaranteed minimum, not the last supported day, so D13's "ended" means "the minimum has passed". If the source also says updates continue, quote that and say so in `notes`, and the site uses the P8 wording, never a bare "support ended". Why: Google's table lists devices past their five-year minimum as still receiving critical security updates.
- D24 A maker's support policy that names no region and states no regional limit is recorded as `GLOBAL`, with a note saying the page names no region. Regional statements (UK PSTI, Australian rules) add their own region. Why: an unqualified statement covers every region, and DATA-POLICY records the regions a statement covers (first used for Google Nest, #21).
- D25 In hand-written YAML, quote any value that contains `: ` or ` #`, or reword it. Why: a plain scalar silently ends at ` #` (a comment), and `npm run validate` still passed when a `seed.yaml` note lost its end this way.
- D26 Parallel agents write scratch files under names unique to their PR or task (for example `pr-35-body.md`), never a shared fixed name. Why: two agents wrote `pr-body.md` at once, and #34 was opened with #35's body.
- D27 Unattended data work runs as a nightly `Crawl` scheduled task (`Patchlife nightly data`, RUNBOOKS O6) following `.agent/prompts/data-refresh.md`, one source per run; the daily build stays in `Default`. Why: the owner chose P1 option B in #30, keeping code work and page reading in separate runs.
- D28 The M2 site is a plain Node build script (`scripts/build-site.mjs`, no new dependency) deployed to GitHub Pages from Actions, with a hand-written search and Lighthouse for the exit checks. Why: the owner chose P2 in #30; it needs no packages, account or secret.
- D29 PDF text and archive snapshots belong to M3, not M1. Why: the owner approved P3 in #30; every M1 source is HTML and PDF support needs a dependency PR.
- D30 D9 allows MPL-2.0 dependencies, such as axe-core inside Lighthouse. Why: the owner approved P4 in #30; GNU lists MPL-2.0 as compatible with GPLv3 and AGPLv3.
- D31 The M4 gates A to C in docs/PLAN.md are approved as written; the owner may adjust the thresholds before day 0, never after. Why: the owner delegated P5 in #30, and fixing the rule before the data arrives stops the result moving the goalposts. The A$ amounts are test thresholds, not prices; prices stay a human gate.
- D32 `disputed` means a correction cites a primary source that conflicts with ours and the conflict can't be settled from primary sources; the site shows "Under review" next to the date until it is settled, then the status returns to `verified` or the record is corrected. Why: the owner delegated P6 in #30; the schema had the status but no rule.
- D33 When a maker gives different dates for the same model in different regions, write one record per region-date, with the region in the id of the record that is not the main one (for example `ring-video-doorbell-4-us`). Why: the owner delegated P7 in #30; it needs no schema change and each record keeps its own evidence.
- D34 For an `at_least` date that has passed, the site says "Minimum support period ended on <date>. <Brand> may still provide updates.", never a bare "ended" (D23). Why: the owner delegated P8 in #30. It is still draft legal copy for the H9a read before the site moves to `patchlife.tech`.
- D35 General web research may use the Firecrawl connector's free credits until they run out, then the built-in WebSearch and WebFetch; manufacturer pages are still read only with the polite fetcher (D17). Why: the owner allowed the free credits on 21 Oct 2026, and nothing in Patchlife may depend on a connector.
- D36 Amends D34: when a record's `conditions` can extend the period for some buyers (today, a condition containing "whichever is later", as in Ring's purchase rule), a passed minimum reads "The published minimum date, <date>, has passed. Some buyers get longer: see Conditions." followed by "<Brand> may still provide updates."; scope or hardware-version conditions keep the D34 wording. Why: for a Ring buyer within four years of purchase, "Minimum support period ended" is false. Still draft copy for the H9a legal read.
- D37 The owner is on Max and aims to move to Pro once the "Getting to Pro" checks in docs/COSTS.md hold. Prefer cost-pivot routes that need neither API credits nor new spend (GitHub Actions, the owner's RX 9070 XT) over ones that do. Why: the owner, 21 Oct 2026; Pro has no included API credits.
- D38 When a source states a support end only as a month and year, store `end_date` as `YYYY-MM`, never as a chosen day. Status treats it as ended only after the month's last day and as ending soon when the month's first day is within a year; the site shows the month and year only. Why: the owner delegated P9 on 21 Oct 2026, and picking a day would round a date, which CLAUDE.md forbids.
- D39 When a maker's own pages give different dates for the same model, record each page's date with the scope that page states (D24, D33), one record per region-date, rather than choosing one; when they agree, one record carries both. Why: the owner delegated the GL.iNet Velica conflict on 21 Oct 2026 (UK PSTI statement against a lifecycle page that names no region).
- D40 The public site stays on GitHub Pages and the repository stays public. Paid services (M6 feed, API keys, reports) run off Pages, first choice on the owner's Unraid server published through the owner's Pangolin VPS. Why: the owner, 21 Oct 2026. Pages is free and CDN-served but bars commercial services; a private repo on a free account would unpublish Pages and drop the ruleset and secret scanning.
- D41 patchlife.tech stays behind Cloudflare's proxy with Cloudflare Web Analytics, and the privacy page says so. Before turning on any Cloudflare feature that sets cookies (Bot Fight Mode, challenges, rate limiting by visitor, Always Online), change the privacy page's "sets no cookies" with the owner's approval first. Why: the owner chose option C in #68 on 21 Oct 2026; Cloudflare lists `__cf_bm` for Bot Fight Mode and `cf_clearance` for challenges, and a plain visit sets none today.
- D42 Routine re-verification runs on GitHub Actions with no model: the nightly `Re-verify evidence` workflow (#80) checks up to 40 records due after 60 days, pushes verification-only changes, and fails visibly when a record can't be checked. The daily build merges its branches (RUNBOOKS A9); `Crawl` sessions re-check the records it couldn't and repair stale ones. This narrows D17 for re-verification only: quotes and audits still come from `Crawl`. Why: every evidence host answered a GitHub runner on 21 Oct 2026, and it removes model use from the most frequent job (COSTS stage 1).
- D43 Archive links come from the Wayback Machine's Save Page Now on GitHub's runners, inside the nightly re-verify run, and an item's `archive_url` is set only when the capture's raw copy holds its quote; `npm run validate` checks the link is a capture of the item's own URL. Filling a null `archive_url` this way merges like a re-verification, without an A8 audit, once the owner approves the merge-rule wording (A9). Why: the `Crawl` proxy refuses archive.org (22 Oct 2026), a runner's anonymous save returned a capture holding the quote in 48 seconds (Probe hosts run 39707946073), and the quote check makes the link as mechanical as a verification, which no session could audit since none reaches archive.org.
- D44 The goal is that Patchlife runs with no AI model and no subscription; `docs/MIGRATION.md` is the plan, and its open decisions are the owner's. Until cut-over, sessions build the plan's replacements and nothing new that needs a model to run. This supersedes D37's Pro target and COSTS stages 3 and 4. Why: the owner, 22 Oct 2026.

- D51 Feed entries are dated by the status rules (`statusSince` in `scripts/status.mjs`: the day a record's last 12 months began, or the day after its published end), never by the build date, and a feed's own date is its newest entry's. Why: a build-date stamp would mark every entry changed daily, so readers would show the same models again and again; the status date says when the event happened (27 Oct 2026, #136).
- D52 A test that reads `git status` must compare before and after, never expect a clean tree: the re-verify workflow runs `npm test` after the archive step has modified `data/`. Why: #138 broke the 27 Oct re-verify run.
- D53 In a workflow, never combine `gh api --slurp` with `--jq`; pipe to `jq`. Why: gh refuses the pair, so `data-gate`'s audited-label check failed on every labelled PR (29 Oct 2026).
- D54 A PR whose base is another `claude/` branch stays a draft until that base has merged; the daily build and the merge rules treat any green `claude/` PR as mergeable into its base. Why: on 1 Nov 2026 the daily build merged B3 (#142) into B2's branch, which was correct by the rules and not what the stack intended.
- D55 A PR that waits on the owner (an `audited` label or a protected path) carries no LOG.md or decisions.md change: put those lines in their own PR that merges at once. Why: on 1 and 2 Nov 2026 the four waiting PRs each appended to LOG.md and every merge put the rest into conflict, so #163 moved their lines to `main`. The nightly prompt's step 7 still appends a line to the data PR (a protected one-line change, not yet opened).
- D56 Never put a closing keyword (`fix`, `fixes`, `fixed`, `close`, `closes`, `closed`, `resolve`, `resolves`, `resolved`) directly before an issue or PR number in a commit message or PR body unless that issue should close when the commit reaches `main`; write `the fix in #154` or `#154's fix`. Why: #163's squash commit said "the gate fix #154" and GitHub closed #154, unmerged, when the commit landed (2 Nov 2026).
- D57 When bringing a branch up to date: check that the fetch succeeded (a fetch that names a missing ref fails as a whole and leaves `origin/main` stale); resolve conflict markers by hand, never `git checkout --ours <file>` or `--theirs` on a file with clean hunks from the other side (it takes the whole file); and gate every push on the exit codes of `npm run validate` and `npm test`, never on a piped tail. Why: on 2 Nov 2026 each of the three put a wrong tree on a PR branch (#135's registry lost #153's lines; #143 was pushed with 26 failing tests), caught by diffing against `main` and by reading the test counts.
- D47 The merge bot (`scripts/merge-bot.mjs`, run by Housekeeping while `BOT_MERGE` is `on`) merges only pull requests that `patchlife-bot[bot]` opened from `claude/reverify-*` or `claude/measures-*` branches in this repository, at the commit it checked, once `test`, `data-gate` and `build` passed and every file fits the PR's type; everything else waits for the owner. The nightly re-verify takes every due record in one run (limit 1000), which amends D42's 40. Why: MIGRATION decision 2; the December wave of about 340 and 355 due records must get through in one night each, and nothing else is safe to merge unread.
- D48 Replaces D20 and narrows D17: the source profiles and rules R1 to R8, the parser gate (the parsers must reproduce every audited record before anything is written) and the owner's sample check (`scripts/audit-sample.mjs`, RUNBOOKS O9) stand in for the second session that audited each data PR. `audited` is the owner's own label; nobody else and no tool adds it. Data the owner writes by hand has no second reader: on a parsed source the parser must reproduce the edit, and on any other source the owner re-reads the record the next day through its highlight link. Why: no model remains to audit, and the verifier proves only that a quote is on the page, not that the record reads it correctly.
- D49 Source profiles in `data/sources/seed.yaml` are binding: `npm run validate` checks every record of a profiled source against its profile (R1 to R8), the registry and the schemas are protected paths, and a profile change needs the owner's `audited` label. A registry change that moves only `last_checked` dates is exempt from both. Why: the profiles hold the judgement the audits used to supply (regions, "at least" wording, conditions, categories, renames).

- D62 A workflow prints text from outside its own code (a PR's file names, a maker's page, a scan's findings) to its log only through `sed -E 's/::/: :/g; s/##\[/# #[/g'`, which breaks up every marker of a workflow command; the files, the run summaries and the PR bodies keep the text as it was. A step's result goes to `$GITHUB_OUTPUT`, never through a command. Why: a probe on a GitHub runner (13 Nov 2026, #215) showed that the runner reads `##[name]` anywhere in a line and `::name::` after any kind of space, a no-break space included, that a disabled command fails the step, and that the gate's earlier cleaning missed both forms. The same probe showed an output written to the file wins over one set by a command, which is why no PR could pass the gate this way.
- D63 The jobs that read makers' pages and push with the App's token stay one job each; the push does not move to a job of its own. A separate job would stop code run from a page's content from taking the token, and nothing in these jobs runs page content: the parsers read the HTML as text with expressions, and the PDF reader, the build of PDF.js in the locked `unpdf` (1.9.1), contains no `eval` and no `new Function` and, with `useWasm` off in `scripts/verify-evidence.mjs`, interprets a PDF's PostScript functions instead of compiling them to WebAssembly. The token is kept from those steps as well: it is never in their environment or in git's configuration (`tests/workflows.test.mjs` checks both), it lasts at most an hour, and it is revoked when the job ends. The risk accepted: a token taken all the same could open and merge a PR that changes scripts, since the ruleset on `main` asks for the `test` and `data-gate` checks and no review; it could not change a workflow, and the gate counts only the owner's own `audited` label. If a job that holds the token gains a dependency that runs or compiles page content, or the App gains permissions, move the push to its own job and require a code owner's review for code (CODEOWNERS, with the owner allowed to bypass). Why: the audit of 14 Nov 2026 (`docs/audits/2026-11-14-workflows.md`, M3), decided by the session on the owner's word of 14 Nov 2026 to do what it judged right.
